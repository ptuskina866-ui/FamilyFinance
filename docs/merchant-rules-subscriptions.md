# Правила магазинов и банковские подписки · 26.10.2026

## Поведение

В редакторе операции банковского счёта можно выбрать «Всегда относить операции этого магазина в выбранную категорию» и понятное название. Сохранение самой правки и правила атомарно. Правила общие для семьи, раздельные для расходов/поступлений. Следующие записи автоматического учёта Приорбанка получают категорию на сервере; категории старой истории, суммы и заметки не переписываются. При последующем проведении/исправлении банка пользовательская категория сохраняется. Связывание старой квитанции с существующей строкой не запускает перекатегоризацию.

Название известного магазина отображается чисто: например, `Retail BLR Minsk MAK.BY` → «Мак.by». Исходное описание остаётся в «Данные банка» и редакторе; личная заметка имеет приоритет в заголовке. Название из правила может отображаться на старых банковских строках, без изменения их исходных полей. Профиль → «Правила магазинов» позволяет удалить правило; уже сохранённые категории остаются прежними. Неизвестные магазины/номера филиалов не объединяются нечётким поиском. Каталог JS/SQL проверяется на совпадение идентичностей.

Существующий поиск ежемесячных расходов расширен кнопкой «Учитывать в плане». Пользователь видит историю, оценку суммы и даты и подтверждает один раз. Сервер заново проверяет 2–6 разных записей одной семьи/банковского счёта/магазина, соседние месяцы, близкие дни, отсутствие другого платежа магазина в этих месяцах и существующего плана. Будущие, отменённые, автоматически созданные расписанием и чужие строки не являются допустимым подтверждением. При изменении истории подтверждение отклоняется; нет плана из придуманных клиентом сумм.

Новый `match_mode=bank` хранит ожидание, а не дополнительный расход. `apply_due_recurring` его пропускает. Реальная банковская операция связывается с планом по счёту, магазину и месяцу, дате ±4 дня и отклонению суммы не более max(1 BYN, 20%). Сохраняется реальная сумма банка, ориентир плана автоматически не меняется. Вторая настоящая покупка остаётся самостоятельным расходом, без второй отметки оплаты плана. Существенные отклонения остаются в журнале и не получают произвольной связи. Отмена освобождает месячную связь; исчезновение операции не считается отменой.

В планах показано «Ждём списание банка» с ориентировочной суммой или «Оплачено в этом месяце» с фактической суммой. Ранняя оплата не резервируется ещё раз в дневном лимите/календаре. Последний день месяца сохраняется как ритм и корректно переходит в февраль/30/31 день. Обычные вручную созданные расписания сохраняют прежнюю логику; автоматического превращения старых расписаний в банковские нет. На момент установки таких старых планов у владельца нет.

## Данные и доступ

- `merchant_rules`: household_id, merchant_key, направление, display_name/category, автор/время; UNIQUE household+merchant+direction. Четыре RLS-политики, явный SELECT authenticated, отсутствие прямой записи/анонимного чтения, Realtime. Запись/удаление только через проверяемые RPC с household lock.
- В `prior_bank_events` добавлены merchant_key/merchant_name/rule_category; серверный триггер связывает предпочтение и реальную банковскую строку. Backfill касается только этих метаданных, не категорий или денег.
- В `recurring_transactions`: match_mode/merchant_key; в журнале recurring_month и уникальная банковская месячная связь. Клиент не может напрямую создать защищённый bank-mode шаблон. Доходы не используются для обнаружения расходных подписок.
- Миграции `20261026065110_merchant_rules_bank_recurring.sql`, `20261026071613_bank_bill_month_end.sql`, `20261026072334_merchant_new_row_guard.sql` зеркалированы секциями 20/21/22 portable schema и установлены. Новая финансовая проекция определяется точно по времени её транзакции; уже существующая строка даже секундной давности не получает новую категорию при legacy adoption. Edge-функции/сессии/секреты/планировщик банковских запросов не менялись.
