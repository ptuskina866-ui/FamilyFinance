# Приорбанк: серверное подключение для телефона · 19.10.2026

Проверка владельцем на iPhone показала архитектурную ошибку предыдущего этапа: `127.0.0.1` указывает на сам телефон, а помощник работал на PC. Новый основной путь выполняет банковские запросы на сервере Supabase; Cloudflare продолжает публиковать интерфейс FinApp. Локальная форма/popup не участвуют в мобильном сценарии.

## Поток и обработка данных

FinApp → «Банки» → «Приорбанк» → «Подключить Приорбанк» открывает форму внутри приложения. Владелец вводит логин/пароль Prior Online, период и явно подтверждает однократный вход через сервер. Карты/история возвращаются в этот же экран; одна карта показывается сразу, несколько требуют выбора. Дальше используется прежняя проверка счёта/категорий/совпадений/итога и подтверждение записи.

Это меняет прежнюю локальную границу: банковские данные для входа передаются по HTTPS серверной функции FinApp и обрабатываются в памяти одного запроса. Пароль и банковские сессии не сохраняются приложением в базе/файлах/хранилище и не выводятся в журналы. В форме это объяснено до отправки и требуется отдельная отметка согласия. Фоновое обновление, сохранённый вход и повторный вход без пароля не реализованы. Обнуление физических строк памяти JavaScript не гарантируется. Используется обычный банковский вход; отдельное банковское право «только чтение» не подтверждено, интерфейс банка остаётся недокументированным.

## Сервер

- Edge Function `prior-connect`: gateway `verify_jwt=true`; дополнительно JWT проверяется через Supabase Auth `/user`. Анонимные/неавторизованные пользователи отклоняются до банковского запроса. Не используются user_metadata/переданный клиентом owner/household. Только POST, точные разрешённые origins, no-store; тело ≤8192 байт, финансовый ответ ≤8 МБ.
- Общие `supabase/functions/_shared/prior/{bank,model,preview}.ts` содержат прежний проверенный протокол, нормализацию сумм и форматов. Локальные модули стали re-export wrappers. Node crypto/buffer — встроенные модули; новых npm-зависимостей нет. В браузер банковский протокол и серверные секреты не попадают.
- Каждый запрос имеет независимые credentials/session; нет общего банковского кеша. Только пять прежних auth/read путей, без платежей/переводов, перенаправлений, автоматических повторов или refresh. Один банковский запрос ограничен 20 секундами, общий банковский этап — 90 секундами. Дополнительная банковская проверка входа останавливается явно.
- До обращения к банку backend-only `claim_prior_connection` проверяет существующего владельца/семью и атомарно получает две аренды — по владельцу и банковскому логину. В `finance_private.prior_connection_attempts` остаются только household/owner, UUID попытки, server-keyed HMAC логина и время; исходный логин/пароль/банковские данные не записываются. Аренда — 120 секунд, минимальный интервал стартов — 60 секунд. Ошибка второй аренды откатывает первую; освобождение требует владельца и UUID. Старая метаинформация удаляется после семи дней при следующем обращении.
- Новая таблица имеет RLS/четыре политики, без клиентских grants и доступа к private schema. Две RPC имеют фиксированный search_path, таймаут и EXECUTE только для service_role. Встроенный серверный ключ используется только функцией для этих RPC/HMAC, не передаётся в банк/браузер и не извлекается в чат/репозиторий.
- Финансовый ответ — строгие исходные snapshots по картам: sourceKey, маска, название, валюты и строки. Сессии, сырые банковские ID, доступный/кредитный баланс и неизвестные поля отсутствуют. Клиент повторно проверяет формат. Получение не меняет ledger/категории/остатки.

Существующий 31-дневный пилот и все правила повторного импорта сохранены. Это не постоянная банковская синхронизация. Данные уже сохранённых операций доступны на телефоне через обычную финансовую базу FinApp.

## Проверки

- `npm test`: 62 проверки. `npm run test:prior`: 20 проверок общего протокола, локального сервера и защищённого backend handler. `npm run test:database`: 5 сценариев / 254 SQL assertions (20 новых), включая свежую и повторную схему.
- Сервер: отсутствие/отказ Auth, чужой origin, неверный метод, неправильные/большие данные и ограничение попыток не начинают банковский вход; текущий Auth user используется владельцем. Нет повторов, отражения секретов ошибок или credentials в ответе. Отмена/ошибка освобождают аренду; сбой освобождения оставляет её истекать.
- SQL: anon/authenticated не вызывают backend RPC и не читают приватную таблицу; один владелец/логин не получают одновременные аренды, конфликт второго ключа откатывает первый, неверный owner/UUID не освобождает аренду, сохраняется cooldown, истечение разрешает следующую попытку. Проверены четыре политики, RLS и SQL mirror.
- Мобильная эмуляция Chromium 320/390 px: inline-форма без popup/loopback, согласие перед отправкой, очищенный пароль, один запрос при двойном нажатии, выбор одной из двух карт, исходные BYN/EUR/комиссия, HTML-описание как текст, локализованная 429 без секретного маркера, отмена без позднего результата. Искусственный API заменял только транспорт внутри изолированного браузера; реальный production service parser и компоненты сохранены. Демо без подмены блокирует реальные подключения. Поля 16 px и даты полной ширины на телефоне, без переполнения. Это не тест на физическом iPhone/WebKit.
- TypeScript/Vite/PWA build пройден: `index-rM2N6tnY.js`; сохраняется прежнее предупреждение размера основного bundle. В bundle нет `127.0.0.1:5188`, имени server-only ключа или банковского сетевого протокола.

## Рабочий backend и база

Edge Function `prior-connect` version 1 ACTIVE, JWT verification включена; entrypoint `supabase/functions/prior-connect/index.ts`. Реальный OPTIONS из рабочего origin вернул 204, отсутствие JWT и поддельный JWT — 401 до банковского входа. Это подтверждает запуск runtime, но не подтверждает доступ банка с IP датацентра или успешный вход пользователя.

Миграция `20261019105902_prior_server_connection.sql` установлена. Прямая проба claim/release под service_role прошла в транзакции с ROLLBACK; таблица попыток пуста. anon/authenticated EXECUTE=false, service_role EXECUTE=true, client SELECT=false, четыре политики. Хэши всех существующих 163 операций, одного счёта и пяти целей до/после совпали. Финансовые записи в рамках проверки не создавались. Security Advisor до/после сохраняет прежние находки: 16 private backups с [RLS без политик](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), 20 намеренных authenticated [финансовых definer RPC](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), прежняя настройка [Auth leaked password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). Новых находок нет.

Supabase Auth/JWT схема сверена с [официальной справкой](https://supabase.com/docs/guides/functions/auth-headers); changelog проверен, будущая деактивация старых TLS 1.2 CBC cipher suites 10.11.2026 не затрагивает современные браузеры/server fetch. Реальные банковские credentials не использовались. Первый серверный вход владельца, серверный доступ к банку, дополнительная проверка и фактическое добавление/баланс ещё требуют проверки. При отказе банка не повторять автоматически и не выдавать это за подтверждённую синхронизацию.
