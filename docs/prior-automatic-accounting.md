# Автоматический учёт Приорбанка · 23.10.2026

## Использование

Открыть Приорбанк, выбрать карту и банковский счёт BYN, один раз включить «Автоматический учёт». При первом связывании начальный остаток должен соответствовать началу сегодняшнего дня. Новые расходы и поступления, включая уже прошедшие операции дня включения, сохраняются без выбора строк и подтверждения каждого импорта. Старые дни не подгружаются в баланс автоматически; для них остаётся прежний проверяемый импорт. Выключение режима и отключение банка не удаляют журнал.

Сервер проверяет банк каждые две минуты, даже при закрытой PWA. Это интервал наших проверок, а не гарантированная задержка банка. Домашний экран показывает последнее успешное обновление/проблему; операции отмечены «Из банка автоматически», редактирование категорий остаётся штатным. При возврате в приложение данные перечитываются; открытая сессия получает записи через прежний Realtime.

## Финансовое поведение и границы

- Импортируется только `history`, ненулевая проверенная сумма по счёту BYN. Исходная валютная сумма/комиссия не подменяет сумму счёта. Дополнительный банковский список не имеет подтверждённого статуса: показывается его количество, но он не влияет на баланс. Его название в протоколе не доказывает, что это ожидающие операции.
- Сохраняются исходные суммы/описания/даты; категории — прежняя общая эвристика, исправляемая пользователем. Никакие старые категории не переклассифицируются. Автоматически не распределяются доходы по накоплениям.
- Используются те же source/day/canonical/occurrence-квитанции, что и ручным импортом. Две одинаковые реальные покупки сохраняют две позиции. Повторная загрузка, изменение/удаление записи пользователем не восстанавливают её автоматически.
- В изменяющемся дне разрешается добавление новых строк, если все ранее импортированные в покрываемом периоде вхождения остаются. Исчезновение/изменение импортированного вхождения останавливает весь финансовый этап атомарно: суммы старых записей не переписываются. Дневные подписи обновляются совместимо с прежним ручным импортом.
- Похожая ручная запись на том же счёте/дне/сумме, редкое совпадение за пределами покрытого окна и явный перевод между своими счетами попадают в «Для сверки». Они не меняют баланс. Их можно явно исключить либо позже добавить обычным импортом/переводом. Это консервативные предупреждения, а не доказанные дубли. Скрытые пользователем исключения сохраняют свои отметки.
- Проверенного стабильного ID операции по-прежнему нет. Автоматического исправления переходов pending → settled, переносов с одновременно изменившимися реквизитами и гарантии полноты истории нет. Неоднозначные движения/возвраты требуют сверки; распознаются только явно обозначенные свои переводы. Прямой канал мгновенных событий банка не подключён.
- Одна карта BYN / один счёт / один владелец. Автоматический диапазон — последние 31 день включая сегодня. После перерыва более 30 дней нужна сверка пропущенного периода. За запуск обрабатываются до двух владельцев; это личный прототип, не заявленная система массовой банковской агрегации.
- При временной сетевой ошибке следующая попытка через 15 минут; при банковском ограничении — через час. Нет немедленных повторов банковских запросов или автоматического входа с паролем. При истечении сессии нужен новый вход, затем расписание продолжится. Пароль не хранится.

## Сервер и доступ

`prior-auto-sync` использует существующий зашифрованный Vault session и owner/login leases. Внутри обращения берётся свежий диапазон, возвращается только финансовый whitelist; завершённые десять дней кешируются для совместимости прежнего экрана. Один запрос не может пересечь привязку owner/household/account/source. Повторное включение/выключение, смена семьи, завершение/удаление сессии инвалидируют поздние ответы по поколениям. Финансовый commit блокирует household так же, как существующие RPC.

Новый HTTP endpoint имеет `verify_jwt=false`, поскольку его собственная аутентификация — одноразовый случайный 256-битный ticket от серверного расписания. Это не пользовательский endpoint. В базе хранится только SHA-256 ticket и двухминутный срок; погашение атомарно, повтор и угадывание не начинают банковский запрос. Результат endpoint — только число проверок/добавлений. В расписании нет банковских паролей, Supabase пользовательских JWT или service-role ключей. Встроенный серверный ключ остаётся внутри Edge runtime.

`prior_automation` и `prior_automation_reviews`: household + owner, восемь RLS-политик, клиентам только SELECT; изменения через ограниченные owner RPC. Ticket-таблица закрыта в `finance_private`, без клиентских grants. Service-only `claim_prior_auto_job` / `complete_prior_auto_job` недоступны anon/authenticated. Метаданные и исключения включены в Realtime; синхронизация не меняет существующий Auth.

Native scheduler вынесен в отдельную миграцию с pg_cron/pg_net. Публичный URL Edge хранится в Vault с именем `finapp_prior_auto_endpoint`; это адрес, не ключ. При настройке проекта он задаётся отдельно. Без включённых владельцем режимов Cron не обращается к банку и не создаёт HTTP-задач.

Security Advisor: два новых намеренно доступных authenticated SECURITY DEFINER RPC проверяют auth.uid/household/owner и привязки; прямые записи в таблицы запрещены. Пояснение класса предупреждения: [Supabase linter 0029](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). Закрытая ticket-таблица с RLS и без разрешающих политик намеренно запрещает клиентский доступ: [linter 0008](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). Прежние замечания backup/RPC/Auth не изменялись.
