# Второй этап: бюджет месяца и назначение дохода

Дизайн сохранён. В «Планах» появилась вкладка «Бюджет»: общие семейные бюджеты категорий, распределение полученного дохода на расходы и цели, календарь регулярных доходов и платежей на 35 дней.

## Попробовать

Открыть локальное демо `http://127.0.0.1:5173/?demo=1` и сбросить его. Затем «Планы → Бюджет»:

1. Создать бюджет еды 400 Br: из него уже потрачено 80 Br, осталось 320 Br. Свободный остаток уменьшится с 1400 до 1080 Br.
2. Распределить зарплату: 450 Br на коммунальные платежи и 200 Br на отпуск. Общий капитал останется 3100 Br; цели станут 1900 Br, бюджеты — 770 Br, свободно — 430 Br.
3. На главной оценка свободных денег на день учитывает оплаченный бюджетом будущий платёж один раз. Покупка из бюджета также не уменьшает свободную дневную оценку второй раз.
4. Попробовать создать бюджет отдельного магазина при активном общем бюджете еды: действие отклоняется с объяснением. Указать 0 в плане категории — её оставшиеся деньги освободятся.
5. Обновить страницу: сохранённые демо-бюджеты и распределение сохранятся, зарплату нельзя распределить повторно.

Каждый доход распределяется один раз. Неиспользованная часть остаётся свободной. Полная отмена распределения пока не реализована; план нужно проверить целиком перед подтверждением. Уже распределённый доход нельзя удалять или уменьшать ниже выделенной суммы. Резервы можно освободить через бюджет категории или цель.

Бюджеты действуют в текущем месяце по общему календарю Europe/Minsk, без автоматического переноса. Новый месяц начинается с нулевых бюджетов. Расходы и история предыдущих месяцев сохраняются. Календарь показывает только сценарий регулярных событий; будущий доход не становится доступным сегодня.

## База и публикация

Миграция `supabase/migrations/20261012_shared_budgets.sql` установлена в рабочую Supabase 12 октября 2026 года. Перед этим сохранён частный снимок текущих операций, целей, счетов и изменяемых функций: `docs/sql/backup-before-budgets.sql`. В снимке включена RLS без клиентского доступа; схема не доступна через Data API.

После установки сравнение подтвердило полное сохранение существующих операций, целей и счетов. Новые бюджеты и распределения не созданы за пользователя. Никакие суммы и категории не переклассифицированы этой миграцией. `finance_schema_version()` остаётся 1 для совместимости установленных клиентов; `finance_planning_version()` возвращает 1.

Новые таблицы имеют household_id, RLS и политики семьи для всех четырёх действий. Клиенту разрешено только чтение; записи проходят через атомарные RPC с проверкой семьи и общей блокировкой. Разделение одного дохода защищено уникальным ограничением и откатом всего действия при любой ошибке.

Рабочий адрес: https://familyfinance.ptuskina866.workers.dev/. Cloudflare собирает GitHub main. Для статического Vite приложения нужны VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY в разделе **Build variables and secrets**. Переменные настроены владельцем; новая сборка первого этапа, экран входа и настоящие Auth/API endpoints проверены. Отсутствующие переменные теперь останавливают сборку до публикации.

## Проверено

- 31 автоматический тест денег, бюджетов, дневной оценки, календаря и гонок профиля.
- 112 исполняемых SQL-проверок обоих этапов: точность, RLS, повтор миграции, пересечение бюджетов еды, недоступный резерв, атомарный откат, повтор распределения, защита исходного дохода и изоляция семей.
- TypeScript, production-сборка и PWA.
- Демо на 320/390 px, подтверждённое смешанное распределение и сохранение данных.
- Действующие таблицы: RLS включена, прямые записи клиенту запрещены, анонимное чтение запрещено.

Авторизованные реальные действия, доставка приглашений, Realtime между устройствами и конкуренция независимых подключений в hosted Supabase пока не проверены. Проверки финансовых действий выполнялись на изолированных тестовых/демо данных.

## Замечания Supabase Advisor

RPC намеренно используют SECURITY DEFINER, проверяют auth.uid()/семью, блокируют household и имеют фиксированный пустой search_path. Внутренние помощники не доступны клиенту. [Описание проверки SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

У частного снимка RLS включена без политик и без grants клиенту: это сознательно закрывает резервную копию для приложения. [Описание RLS without policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

Существовавшее ранее замечание: защита Supabase Auth от утёкших паролей выключена; эта настройка не менялась в функциональном релизе. [Пояснение Supabase](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
