# Быстрый учёт и автоподключение Приорбанка · 25.10.2026

## Поведение

При включённом автоматическом учёте запрашивается быстрый режим. Первый проход проверяет свежий ответ банка и сопоставление с квитанциями/ручными записями без создания событий или денег. После успешной проверки следующий проход начинает учитывать предварительные расходы и поступления. Минутный Cron, кнопка обновления v2 и возврат в приложение используют общую очередь и owner/login lease с ограничением частоты. Открытие раздела сразу показывает кеш; старый ручной импорт находится в раскрываемом блоке. Минутное расписание — цель частоты проверок, а не гарантия задержки банковского API; lease, сетевые ошибки и ограничения банка могут увеличить интервал.

Отдельное разрешение в форме подключения сохраняет логин и пароль интернет-банка зашифрованными в Supabase Vault. Обычная сессия используется первой; лишь явное истечение/HTTP 401 разрешает один повторный вход под уже занятым lease. SQL ограничивает повторное получение секрета десятью минутами. Сетевая ошибка, 403, банковское ограничение не запускают повторный вход. Неверный пароль, блокировка и дополнительное подтверждение отключают автоматический вход до участия владельца. Разрыв подключения, выход из семьи и удаление владельца очищают сохранённые секреты. Клиентского хранения пароля, собственного Supabase Auth или сохранения пользовательского JWT нет.

На момент подготовки выпуска прежняя рабочая сессия уже завершена; старый пароль не сохранялся. Владельцу потребуется один раз войти в новой форме и включить автоподключение. Свежий реальный банковский ответ и физический iPhone нельзя проверить без этого действия. Пароль не нужно передавать в чат.

## Финансовая модель

- В основной истории сумма счёта берётся из `accountAmount`. В дополнительном списке сумма счёта равна `-amount`; отдельная валютная сумма — `transAmount`. Время `transTime` сохраняется, исходный календарный день остаётся банковским. Эти протокольные различия сверены с [конвертером Приорбанка Дзен-мани](https://github.com/zenmoney/ZenPlugins/blob/master/src/plugins/priorbank/converters.js) и его примерами; новый код реализован в существующей архитектуре FinApp.
- Внутренний финансовый снимок v2 передаётся только серверным RPC. Публичный ответ v2 содержит старые снимки v1 и строго проверяемые булевы признаки режима/автоподключения. v1 connect/sync/status и файлы сохраняют прежние оболочки: старые клиенты не получают неизвестные поля. Пароли, токены, баланс банка и необработанные ответы не попадают в публичный DTO.
- `prior_bank_events`: owner/household/account/source, внутренний ID, псевдонимы вхождений, время/суммы/валюта, `provisional/posted/cancelled/needs_review`, связанная запись журнала и аудит. Таблица доступна семье только для чтения, записи идут через ограниченные RPC; явные grants и четыре RLS-политики. Все финансовые операции сериализованы household lock и проверяют поколения подключения/режима. Более старый снимок не откатывает более свежий commit.
- Предварительная запись сразу влияет на баланс и аналитику. Однозначное проведение меняет ту же запись, не категорию/заметку. Изменение суммы сохраняет предыдущую сумму и пометку «Изменено банком». Полный явно обозначенный `Reversal. Retail` отменяет только одну однозначно совпавшую покупку; несколько кандидатов требуют сверки. Обычные зачисления/возвраты не считаются отменой по одному знаку.
- Отмена даёт нулевой эффект той же транзакции; исходная сумма и история остаются в банковском событии. Нулевая сумма разрешена финансовым триггером только привилегированному reconciler для уже связанного отменённого события; произвольная нулевая запись клиента запрещена. В журнале исходная сумма зачёркнута. Накопления/бюджеты не перераспределяются, дефицит показывается явно.
- Повторы сопоставляются по карте, времени, направлению, валюте, описанию и вхождениям. Две реальные одинаковые покупки сохраняют два вхождения. Удаление оставляет suppression и квитанции. Старая автоматическая запись связывается только при однозначном неизменённом соответствии и существующей квитанции; исходные финансовые записи не переимпортируются. Ручные совпадения и неоднозначные изменения остаются для сверки. Подтверждение сверки проверяет актуальные сумму/статус, сохраняет категорию/заметку и не связывает произвольно чужую транзакцию.
- Исчезновение из списка, изменение доступного баланса или имя дополнительного списка не доказывают отмену. Без стабильного банковского ID неоднозначный перенос даты/описания/суммы не сливается автоматически. Валютная ранняя запись без оригинальной валютной суммы, нулевые/непроверенные данные требуют сверки; курс не вычисляется. По-прежнему одна карта BYN/один счёт, окно до 31 дня, длительный пропуск требует сверки.

## Сервер и выпуск

Установлены portable `20261025153840_prior_live_accounting.sql` и native `20261025155532_prior_live_scheduler.sql`; native job обновляется, не дублируется. `prior-connect` v4 ACTIVE (`verify_jwt=true`), `prior-auto-sync` v4 ACTIVE (собственная аутентификация одноразовым ticket, прежний `verify_jwt=false`). [Supabase Vault](https://supabase.com/docs/guides/database/vault) остаётся единственным хранилищем банковских секретов; новые клиентские таблицы имеют явные grants, совместимые с [изменением Data API](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

Native rollback probe `tests/prior-live-native-probe.sql` прошёл на рабочем Supabase с вымышленным владельцем: Vault encryption и отсутствие пароля в load, shadow без денег, предварительные расход/доход, точный баланс 137.67, повтор без дублей, однократное получение секрета под lease, disconnect/удаление секретов и доступы. Все синтетические пользователи, подключения, деньги, события и секреты откатились. Банковские endpoints в этом тесте не вызывались.

Native ticket → Edge HTTP 200 (`checked:0, imported:0`), без обращения к банку при завершённой сессии. Единственный `finapp-prior-auto` активен с `* * * * *`. После установки и rollback probe рабочий журнал содержит те же 178 записей; контрольные суммы журнала `e52422841eb9c877fb12a7d6f0325cfc`, счетов `9be1e245d9098c8e4163c575052cd90c`, целей `e332abbcb7acdb95de5414cdfe4e1bfa` совпадают с исходными.

Для единственного существующего включённого подключения выставлен только запрос быстрого режима (`live_requested=true`); `live_enabled=false`, причина `reauth`. После нового входа shadow проверит свежий ответ до любых новых финансовых записей. Новые секреты за владельца не создавались, прежняя история массово не импортируется.

Повторный Supabase Advisor: новых RLS/доступов к секретам не обнаружено. Три новых owner/household-проверяемых RPC намеренно доступны authenticated как [SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable); это отмечается линтером и покрыто изоляционными тестами. Новые индексы ещё не использовались до активации. Прежние замечания к закрытым backup/ticket таблицам, старым политикам и настройке защиты Supabase Auth сохранены; они не менялись этим выпуском.

Публикация интерфейса и финальная проверка публичных ресурсов будут дополнены после завершения выпуска. Реальная скорость и обработка нового платежа на физическом iPhone остаются проверкой после повторного входа владельца.
